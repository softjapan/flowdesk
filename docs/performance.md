# 性能の計測と改善（第15章）

確認日：2026-11-25。N-04「一覧画面は顧客 1 万件・予約 10 万件で p95 500ms 以内」を確かめるために計測し、改善の前後を比べた。
**この文書の数値は、すべて下記の環境で実際に計測したもの**（推定や理論値は書かない）。

## 結論

| 画面 | N-04（p95 500ms） | 改善前 → 改善後の p95（同時 1） | 改善前 → 改善後の p95（同時 10） |
|------|:----:|------|------|
| ダッシュボード（S-06） | 満たす | 115 → 32 ms | 1,416 → 191 ms |
| 顧客一覧（S-09）1 ページ目 | 満たす | 486 → 25 ms | 5,265 → 130 ms |
| 顧客一覧 500 ページ目 | 満たす | 490 → 35 ms | 4,482 → 124 ms |
| 顧客一覧 検索 | 満たす | 96 → 73 ms | 873 → 116 ms |
| 予約カレンダー 日（S-07） | 満たす | 72 → 28 ms | 991 → 214 ms |
| 予約カレンダー 週（S-07） | 同時 5 までは満たす | 172 → 113 ms | 1,394 → **561 ms** |
| 予約の作成（S-08、一覧ではない） | 同時 5 までは満たす | 142 → 94 ms | 1,776 → **590 ms** |

- 一覧画面の遅さの原因は DB ではなかった。DB のクエリはどれも数 ms〜十数 ms で、**Node の側で 1 万行を受け取って並べ替えていたこと**と、**同じ描画が 1 回のリクエストで 2 回実行されていたこと**（後述）が主な原因だった
- 週表示と予約の作成は、同時 10 本（待ち時間なしで送り続ける）では p95 が 500ms を超える。原因は件数の総数（10 万件）ではなく、**1 画面に出す量**（週表示は 702 行・本文 92 万文字、予約の作成は顧客 9,900 人の選択肢・本文 123 万文字）の描画にかかる CPU。同時 5 本では 288ms・335ms だった（[残っている課題](#残っている課題)）
- N+1 は前日リマインドの登録（Worker）にあり、クエリ数が予約の数に比例していた（150 → 10）
- インデックスは追加しない。実行計画で、一覧のクエリは既存のインデックスか、1 万件の全件走査（数 ms）で足りることを確かめた
- ダッシュボードのキャッシュは入れない。DB での集計にした後は、ダッシュボード固有のクエリは 6ms 前後で、キャッシュで省ける時間より、テナント・ロールの境界と予約の反映の遅れの危険の方が大きい

## 計測の方法

### 環境

| 項目 | 値 |
|------|----|
| マシン | Apple M1（8 コア）・メモリ 16GB・macOS。Docker Desktop の VM に 8 CPU・8GB |
| DB | `postgres:18.7`（Docker）。設定は既定のまま（`shared_buffers` 128MB・`work_mem` 4MB） |
| アプリ | Node.js 24.13.0。`next build` → `next start`（本番モード、1 プロセス）。DB とは同じマシンの Docker のポート越しにつなぐ |
| そのほか | 計測中も他のアプリ（ブラウザ・動画編集ソフト）が動いており、ロードアベレージは 5〜14 だった。改善前と改善後は、同じ時間帯に続けて計測した（13:29〜13:39）。同時 10 本の p95 は、同じビルドでも回によって 1〜2 割ほど変わった |

本番の構成（第16〜17章の ECS・RDS）とは CPU もネットワークも違う。数値は**改善の前後の比較**に使い、本番の性能の保証には使わない。

### データ（`npm run perf:seed`）

`scripts/perf/seed-large.ts` が、シード（`npm run db:seed`）の上にデモサロン（`org_a`）の行を足して N-04 の規模にする。SQL の `generate_series` で作るので 16 秒で入る。

| 項目 | 件数 |
|------|------|
| 顧客 | 10,000（うち論理削除 100。シードの 33 件を含む） |
| 予約 | 100,000（今日の 800 日前〜200 日後。シードの 152 件を含む）。全組織では 100,100 |
| スタッフ | 20（シードの 3 人＋計測用 17 人。Free の上限を超えるので組織を Pro にする） |
| 1 日の予約 | 100 件（20 人 × 10・12・14・16・18 時）。今月は約 3,000 件、今週は 702 件 |

過去の予約の 1 割はキャンセル、残りは来店済み。今日以降は 3 分の 1 が仮予約、残りが確定。最後に `VACUUM ANALYZE` で統計情報を更新する。
計測が終わったら `npm run db:seed` で元に戻す。

### 計測の道具（依存は追加していない）

| コマンド | 内容 |
|----------|------|
| `npm run perf:bench` | `scripts/perf/bench.ts`。画面と同じ Service を、デモユーザー（Owner）の文脈で 30 回ずつ順に呼び、所要時間の p50・p95 と、1 回あたりのクエリ数（Prisma の `query` イベント）を出す |

## 改善前の計測で分かったこと

### Service 単位（`npm run perf:bench`、30 回）

| 処理 | クエリ数 | p50 | p95 |
|------|:----:|----:|----:|
| 顧客一覧 1 ページ目 | 1 | 158.5 ms | 192.8 ms |
| 顧客一覧 500 ページ目 | 1 | 150.5 ms | 163.7 ms |
| 予約カレンダー 週 | 4 | 32.3 ms | 40.1 ms |
| ダッシュボード（Owner） | 5 | 38.8 ms | 56.4 ms |
| 予約フォームの選択肢 | 4 | 35.0 ms | 41.6 ms |
| 前日リマインドの登録（Worker） | **150** | 66.5 ms | 72.6 ms |

一方、DB の実行時間は短かった（`EXPLAIN ANALYZE`）。

| クエリ | 実行計画 | 実行時間 |
|--------|----------|---------:|
| 顧客を全件（1 万件）ID 順に | `customer_pkey` の Index Scan | 3.3 ms |
| 今週の予約（702 件） | `reservation (organizationId, startsAt)` の Index Scan | 0.6 ms |
| 今月の予約（3,008 件） | 同じインデックスの Bitmap Heap Scan | 4.2 ms |

つまり時間の大半は、1 万行を Prisma で受け取って JavaScript のオブジェクトにすることと、`localeCompare("ja")` での並べ替え（1 万件）に使われていた。顧客一覧だけでなく、カレンダー・ダッシュボード・予約フォームも、予約の顧客名を引くためだけに組織の顧客を全件読んでいた。

### 同じ描画が 2 回実行されていた

画面ごとのクエリ数を DB のログで数えると、**どの画面も同じクエリの組が 2 回ずつ**、別々の接続から同時に実行されていた（例：顧客一覧の 1 回のリクエストで `session`・`user`・`organization`・`member`・`location`・`customer`・`customerExport` が 2 回ずつ、計 14 文）。

原因は `next.config.ts` の `partialPrefetching: true`。Next.js 16.4.6 は、ページの描画と並んで、プリフェッチ用の描画（ランタイムのプリレンダー）を同じリクエストで実行し、その結果を最初の RSC のペイロードに埋め込む（`node_modules/next/dist/server/app-render/app-render.js` の `spawnRuntimePrefetchWithFilledCaches`）。この描画でも Cookie とヘッダーは読めるので、セッションの確認から先の DB の読み込みがすべてもう一度走る。DB の結果はキャッシュしていないのでプリフェッチの結果には入らず、捨てられるだけだった。同梱のドキュメント（`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/02-route-segment-config/prefetch.md`）にも「Cookie やヘッダーを読むページは、プリフェッチのたびにサーバーで描画し直すので CPU を使う」とある。

## 改善したこと

### 1. プリフェッチの描画で DB を読まない（`src/server/session.ts`）

`getSession` の最初で `await connection()` する。`connection()`（と `io()`）の後のコードは、ビルド時でもプリフェッチでも、プリレンダーから外れる（同梱のドキュメント `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/io.md`）。ログインの確認から先はすべて利用者のリクエストでだけ実行される。

`partialPrefetching` 自体は止めない（サイドバーのリンクの App Shell のプリフェッチは残す）。DB の結果は元々プリフェッチに入っていなかったので、画面の動きは変わらない。

画面ごとの DB の文の数（1 回のリクエスト）：

| 画面 | 改善前 | 改善後 |
|------|----:|----:|
| ダッシュボード `/demo-salon` | 20 | 11 |
| 顧客一覧 `/customers`（1 ページ目・500 ページ目） | 14 | 7 |
| 予約カレンダー `/reservations` | 18 | 10 |
| 予約の作成 `/reservations/new` | 18 | 9 |
| 予約の詳細 `/reservations/[id]` | 22 | 11 |
| 顧客の詳細 `/customers/[id]` | 16 | 8 |
| メンバー `/members` | 24 | 12 |
| 監査ログ `/audit-logs` | 16 | 8 |
| 料金プラン `/billing` | 16 | 8 |
| 店舗 `/locations` | 18 | 9 |
| メニュー `/services` | 12 | 6 |
| 組織の選択 `/orgs` | 8 | 4 |

改善後の 11 文（ダッシュボード）の内訳は、セッション 2（`session`・`user`、Better Auth）、組織の文脈 3（`organization`・`member`・`location`）、ダッシュボード 6（集計 2・本日の予約 1・その顧客・メニュー・担当 3）。

### 2. N+1：前日リマインドの登録（`scheduleReminders`、Worker）

組織 → 店舗 → 明日の確定済みの予約、とたどり、**予約 1 件ごとに `insertJob`（`createMany` と ID を引く `findUnique` の 2 クエリ）**を呼んでいた。デモサロンの明日の確定済みの予約は約 70 件で、1 回の実行が 150 クエリになっていた。

ジョブを配列に集めて、最後に `insertJobs`（`createMany` 1 回＋`idempotencyKey` の `IN` で ID を引く `findMany` 1 回）で作るようにした。

| | クエリ数 | p50 | p95 |
|---|----:|----:|----:|
| 改善前 | 150 | 66.5 ms | 72.6 ms |
| 改善後 | 10 | 14.4 ms | 20.4 ms |

組織ごと・店舗ごとの読み込み（組織 1＋店舗 1 ずつ）は残した。どちらも `organizationId` で絞り込む規約（`CLAUDE.md`）を守るためで、数は予約ではなく組織と店舗の数で決まる。

回帰テスト：`src/server/services/performance.db.test.ts`「明日の予約が増えても、クエリの数は変わらない」。明日の予約を 6 件足す前後でクエリ数を比べる（`test/query-count.ts`）。修正前のコードでは「32 クエリ（期待 20）」で失敗することを確かめた。

### 3. 顧客一覧の検索・並べ替え・ページングを SQL に寄せる（`searchCustomers`）

これまでは Repository のコメントで「電話番号のハイフンを無視する検索を SQL に寄せるかは第15章で計測して決める」としていた。計測の結果、全件を読む方式は 1 万件で 1 回 150ms かかるので SQL に寄せた。

- 氏名・フリガナ・メール：`lower(regexp_replace(列, 空白, '', 'g'))` に検索語が含まれるか（`strpos`。`LIKE` を使わないので `%`・`_` を文字として扱える）
- 電話番号：`regexp_replace(phone, '[^0-9]', '', 'g')` に検索語の数字が含まれるか
- 並び：`ORDER BY "nameKana" COLLATE "ja-x-icu", id COLLATE "C"`。列の照合順序（`en_US.utf8`）のままだと、濁点・半濁点の扱いが以前の `localeCompare("ja")` と変わる（コードポイント順では ハナ・バア・パイ の順、ja では バア・パイ・ハナ）。ICU の `ja` で並べ、Node と同じ順になることをテストで確かめた
- 件数は `count(*) OVER ()` で同じクエリから取る。範囲外のページでは件数も返らないので、そのときだけ読み直す

予約フォームの顧客の選択肢も、必要な列だけを同じ順で SQL から取るようにした（`listCustomerOptions`）。

### 4. 予約の顧客名などを、予約と一緒に取る（`listReservationsWithNames`）

カレンダー・ダッシュボードは、予約の顧客名・メニュー名・担当名を引くために、組織の顧客（1 万件）・メニュー・スタッフを全件読んでいた。予約の `select` で関連（`customer`・`service`・`staffProfile`）の名前だけを取るようにした。Prisma 7 の既定（`relationJoins` はプレビュー機能のため使っていない）では、予約 1 回＋関連ごとに 1 回（`(organizationId, id) IN (...)`）の計 4 クエリになる。クエリ数は予約の件数によらない。

論理削除した顧客と無効になったスタッフは、以前（有効な顧客・スタッフの一覧から名前を引いていたとき）と同じく「（不明）」と表示する。

### 5. ダッシュボードの集計を DB で行う

今月の予約（約 3,000 件）と直近 14 日の予約（約 1,400 件）を読んで Node で数えていたのを、`count(*)`・`count(DISTINCT "customerId")`・`sum("priceYen")` と、`to_char("startsAt" AT TIME ZONE 店舗のタイムゾーン, 'YYYY-MM-DD')` での `GROUP BY` にした。行を読むのは本日の予約だけ。売上は Staff には返さない（Service で判定する。`canViewRevenue`）。

### 6. 数百行の表の出力を減らす

週表示（702 行）は、DB の処理が 13ms でも、同時 10 本で p95 が 1 秒を超えていた。1 行の HTML が 1,475 文字あり、同じ量が RSC のペイロードにも入っていた。

| 試したこと | 本文（週表示） | 同時 10 の p95 |
|------------|----:|----:|
| 1〜5 を入れた後 | 1,985,981 文字 | 794 ms |
| 状態のバッジ（`StatusBadge`）を、見た目に効くクラスだけにする | 1,367,099 文字 | 600 ms |
| 行・セルのクラスを、各 `<td>` ではなく `tbody` の子孫セレクタで当てる（`CompactTableBody`） | 920,008 文字 | 573 ms |
| （実験、採用しない）各行の `<Link>` を `<a>` にする | 917,859 文字 | 561 ms |

バッジは、Badge の約 800 文字のクラスのうち、リンク・フォーカス・アイコン用（文字だけの状態表示には効かない）を除いた。`<Link>` を `<a>` にしても差は誤差の範囲だったので、クライアントでの遷移を残すため採用しなかった。残りは 700 行分の React の描画そのものと考えられるが、CPU プロファイルは子プロセスの分を取れず、内訳は確かめていない。

### 7. 顧客一覧の画面の直列の待ち

`listCustomers` と `listCustomerExports`（CSV エクスポートの履歴）を順に待っていたのを `Promise.all` にした。後者は 1 クエリ（1ms 未満）なので、計測で分かる差はない。

## ダッシュボードのキャッシュ（第5章で見送ったもの）

**入れない**。計測の結果：

- 改善後のダッシュボード固有のクエリは 6 本で、Service 全体で p50 6.0ms・p95 7.6ms（Owner）。画面は同時 1 で p50 21ms・同時 10 で p95 191ms で、残りの時間はセッションの確認と描画。キャッシュで省けるのは 1 リクエスト数 ms
- 入れる場合に必要なことと危険：
  - **テナント・ロールの境界**：キャッシュの鍵に `organizationId` と「売上を見られるか」（`canViewRevenue(role)`）を必ず含める。ロールを鍵に入れ忘れると、Owner の売上が Staff に出る。売上を含まない部分と含む部分で鍵を分けることになる
  - **日付の境界**：「今日」「今月」は店舗のタイムゾーンで決まる。鍵に `todayYmd` を入れないと、日付が変わっても前日の「本日の予約」が出る
  - **予約の変更の反映**：予約の作成・変更・キャンセルの Server Action で `updateTag(組織のタグ)` を呼ぶ。反映を忘れた経路（今後の Worker・管理の操作・Webhook など）があると、その分だけ古い数字が出る。`cacheLife` を短く（例：1 分）しても、その間は自分の変更が見えない
  - **複数のインスタンス**：既定の `use cache` はインスタンスごとのメモリに置く。ECS で複数のタスクを動かすと、`updateTag` は呼んだタスクのキャッシュしか消さない。`use cache: remote` とキャッシュハンドラー（Redis など）が要る
- 入れ直す目安：今月の集計のクエリが 50ms を超える（1 か月の予約が今の 10 倍の 3 万件程度になる）か、ダッシュボードが DB の負荷の上位に出たとき。そのときも、まず集計用のインデックス（`(organizationId, startsAt) INCLUDE (status, "priceYen", "customerId")` の Index Only Scan）を試す

## ストリーミング（Suspense）

検討して、**今回は分けない**。

- どの画面も、静的なシェル（サイドバーと `loading.tsx` の「読み込み中」）は TTFB 2〜5ms（同時 1）で届いている
- ダッシュボードの 3 つの区画（今月の実績・予約推移・本日の予約）は、データの取得がどれも数 ms で、別々の Suspense にしても先に出せる時間はほとんどない
- 週表示で遅いのは 700 行の描画で、データの取得（13ms）ではない。見出しと絞り込みのフォームを先に出すことはできるが、表そのものは Suspense では速くならない。分けるなら、日ごとに別の境界にして上の日から順に出す形になり、Service を「枠（日付とスタッフ）」と「日ごとの予約」に分ける変更になる。体感の改善の量を計測してから決める（次の課題）

# 障害対応で Claude Code を使う手順（第18章）

アラーム（`docs/observability.md` の 4）が鳴ったときに、Claude Code にログ・メトリクス・トレースを読ませて**原因の仮説**を出させる手順。演習の結果は最後の「8. 演習の記録」。

## 1. 任せること・任せないこと

| | Claude Code に任せる | 人が行う |
|---|---|---|
| 読む | 集めた資料（下の 3）とリポジトリのコードを読み、仮説を順位つきで出す。仮説ごとに根拠（ログの行・メトリクス・トレースのスパン・コードの場所）と、確かめる方法を挙げる | 資料を集める（本番の認証情報を持つのは人だけ） |
| 確かめる | 手元で再現する手順・読み取りだけのクエリ（Logs Insights・`SELECT`）を書く | 本番でクエリを実行する。結果を次の資料として渡す |
| 直す | 修正の差分を PR として作る（通常の CI・レビューを通す） | 復旧の操作（ロールバック・再起動・再実行・DB の変更）を決めて実行する。お客様への連絡 |

**任せない**：本番の AWS の操作（Claude Code の端末に本番の認証情報を置かない。第17章の OIDC のロールも渡さない）、DB への書き込み、DLQ の削除・再投入、デプロイ。Claude Code の答えは仮説であり、根拠の行を人が見て確かめてから動く。

## 2. 渡さないもの

- 秘密：`.env*`、Secrets Manager の値、`DATABASE_URL`、Stripe・SMTP の鍵、Cookie、セッションのトークン、署名付き URL（`CLAUDE.md` の禁止事項と同じ）
- 個人情報：顧客・スタッフの名前・メールアドレス・電話番号・メモ、メールの本文、DB の行そのもの（`SELECT *` の結果）、DLQ のメッセージを開いた中身の payload
- 生のログ（アプリのログは `src/server/logger.ts` で伏せてあるが、RDS の `postgresql` ログ・ALB のアクセスログ・Next.js 以外のログは伏せていない）

アプリのログは書き出すときに伏せてある（メールアドレス → `[email]`、電話 → `[phone]`、接続文字列の資格情報・トークン → `[REDACTED]`）。それでも渡す前に、下の 4 の検査を必ず実行する。

## 3. 渡すもの（資料の束）

1 つのディレクトリ（`incident-<日時>/`）にまとめ、その中だけを読ませる。

| ファイル | 中身 | 本番での集め方（未確認：本物の AWS では実行していない） | 手元での集め方 |
|---|---|---|---|
| `summary.md` | 鳴ったアラームの名前・時刻、利用者からの報告（何が・いつから）、直近のデプロイ（版・時刻） | アラームのメール、`aws ecs describe-services` の deployments | 手で書く |
| `metrics.json` | キューの件数・最も古いメッセージの年齢・DLQ、5xx の割合、p95、RDS の CPU・接続数（障害の前後 1 時間） | `aws cloudwatch get-metric-data`（ダッシュボードの式と同じ） | ElasticMQ の `GetQueueAttributes` |
| `errors.json` | エラーのログをメッセージ・コードごとに数えたもの | Logs Insights の保存クエリ `errors-by-message`、`failed-jobs` | worker・web のログの `level=error` を集計 |
| `logs.jsonl` | 障害の時間帯のエラーの行（最大 200 行）と、代表のトレース ID の行すべて | Logs Insights の `by-trace-id` | `grep '"level":"error"'` |
| `trace.txt` | 失敗したジョブ・リクエストのトレース 1〜3 本（スパンの木） | X-Ray のトレースの画面・`aws xray batch-get-traces` | Jaeger の API（`/api/traces/<ID>`） |
| `tasks.txt` | ECS のタスクの状態・止まった理由（`EcsTaskStops` のロググループ） | `aws ecs describe-tasks`、`/aws/events/flowdesk-prod/ecs-task-stopped` | `docker compose ps` |
| `changes.txt` | 直近のコミット（`git log --oneline -10`） | 同じ | 同じ |

どのファイルにも**集めた時刻（UTC）と対象の時間帯**を先頭に書く（演習で、`tasks.txt` に時刻がなく、プロセスの経過時間から起動の時刻を推測させてしまった）。

**DLQ は `get-queue-attributes` で数えるだけにする。** `receive-message` で中を見ると、受信の回数と可視性が変わる（読み取りのつもりでも状態を変える）。中身（payload の宛先・本文）も渡さない。

## 4. 渡す前の検査

```bash
# メールアドレス・電話番号・鍵の形・接続文字列が残っていないか（0 件であること）
grep -rEn '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}|0[0-9]{1,4}-[0-9]{1,4}-[0-9]{3,4}|sk_(live|test)_|whsec_|postgres(ql)?://[^@[]+@' incident-*/
npm run secrets:scan   # リポジトリの秘密の検査（第14章）。資料の束はリポジトリに入れない
```

## 5. Claude Code への依頼

資料の束のディレクトリとリポジトリだけを読める状態で、次の依頼を渡す（読み取りの道具だけを許す。`claude -p --allowedTools "Read,Grep,Glob"` など）。**原因の見当は書かない**（誘導すると、それに合う根拠だけを拾う）。

```text
本番の障害の調査を手伝ってください。資料は incident-<日時>/ にあります（summary.md から読む）。
アプリのコードはこのリポジトリです（docs/architecture.md・docs/observability.md に構成）。

1. 起きていることを、資料の事実だけで 3 行にまとめる
2. 原因の仮説を可能性の高い順に最大 3 つ。仮説ごとに：
   - 根拠（資料のファイルと行、コードの場所）
   - 反する事実・まだ分からないこと
   - 確かめる方法（読み取りだけのクエリ・コマンド。本番で人が実行する）
3. 利用者への影響（何が失われた・遅れた可能性があるか）
4. 復旧の選択肢と、それぞれの危険（実行はしない）

資料にないことは推測と明記する。資料・コードを変更しない。AWS・DB に接続しない。
```

## 6. 復旧（人が行う）

- 原因を直してから再実行する。DLQ の主な原因（第11章、`MAX_ATTEMPTS = 3`）：SMTP・S3・DB に接続できない、payload の誤り
- **DLQ のメッセージを本体のキューに戻すだけでは再実行されない。** 3 回失敗したジョブは DB で `failed` になり、`runJob` は届いたメッセージを「終わった」として捨てる。`npm run jobs:retry` で DB の job を `queued` に戻して送る（`scripts/ops/retry-failed-jobs.ts`。本番は ECS の run-task で実行する）：

  ```bash
  npm run jobs:retry -- --since <障害の始まり（ISO 8601）>                      # 数えるだけ
  npm run jobs:retry -- --since <障害の始まり> --type mail.send --apply         # 再実行
  ```

  DLQ に残ったメッセージは、再実行した後なら消してよい（受け取っても何もしない）
- 予約のメール（`reservation.*`）は、処理する時点で予約の日時が変わっていれば送らない（第11章）。古い確定メールを再実行しても、日時が変わった予約には送られない
- **パスワード再設定のメールは、依頼から 60 分でリンクが切れる**（`src/server/auth.ts`）。障害から 60 分を過ぎてから再実行すると、切れたリンクを送る。`jobs:retry` は種類（`mail.send`）でしか絞れず、再設定のメールだけを外せないので、60 分を過ぎていたら、再設定のメールは利用者に依頼し直してもらう案内を先に出し、`--since` を 60 分以内に絞る
- DB の誤った変更・削除は `docs/runbooks/restore.md`（PITR）

## 7. 振り返りに残すこと

時刻の流れ（検知・最初の仮説・原因の確定・復旧）、Claude Code の仮説のうち当たったもの・外れたもの、渡した資料で足りなかったもの、監視（アラーム・ログ）で直すこと。

## 8. 演習の記録（2026-11-25、手元）

### 再現した障害

docker compose の Mailpit（SMTP）を止め（`docker compose stop mail`）、顧客の CSV エクスポートを 3 回と、パスワード再設定を 1 回依頼した。CSV は S3 に書けたが、完了のメール 3 通と再設定のメール 1 通が送れず、それぞれ 3 回失敗して DLQ に入った。Worker と web は動いたまま（Worker を止めたのではなく、Worker の外の依存が止まった）。

### 時刻の流れ（UTC）

| 時刻 | 出来事 |
|------|--------|
| 19:07:51 | SMTP を止めた（障害の始まり） |
| 19:07:53 | 最初の `ジョブが失敗`（`ECONNREFUSED 127.0.0.1:51025`） |
| 19:08:34 | 4 通とも 3 回目の失敗（`final: true`） |
| 19:09:34 | DLQ に 4 件（手元はキューを 3 秒ごとに見て検知。本番の `dlq-not-empty` は 5 分の期間なので、ここから最大 5 分遅れる。`app-errors` は 12 件 ÷ 2 期間で閾値に届かず鳴らない） |
| 19:10:07 | 資料の束を集め終えた（33 秒。3 の表の手元の集め方。4 の検査で `changes.txt` のコミットのメッセージの `sk_live_` の文字が 1 件当たったが、鍵ではなかった） |
| 19:11:49 | Claude Code（新しいエージェント、読み取りだけ、原因の見当を伝えない）が仮説を返した（102 秒） |
| 19:12:11 | 人が SMTP を戻し（`docker compose start mail`）、`npm run jobs:retry` で数えて（`mail.send: 4 件`）、`--apply` で再実行 |
| 19:12:13 | 4 通が Mailpit に届いた。DB の job は 4 件とも `succeeded`。DLQ の 4 件を消した |

検知から復旧まで約 2 分 40 秒、障害の始まりから約 4 分 20 秒。

### Claude Code の答え（要点）

- 事実のまとめ：`mail.send` の 4 件がそれぞれ 3 回失敗し DLQ に 4 件、web は正常（5xx 0・p95 168ms）、CSV は S3 まで成功して完了メールで失敗（`trace.txt` の行を挙げた）
- 仮説 1（**当たり**）：Worker の接続先の SMTP（`localhost:51025`）が止まっている。`ECONNREFUSED` はタイムアウトではなく即座の拒否で、待ち受けがない。確かめ方に `docker compose ps` とポートの確認、本番なら Logs Insights で `ESOCKET` の件数が続いているか
- 仮説 2：SMTP の設定が本番の想定（SES の 587）と違う（Terraform の値とコードの既定値を挙げた）。直近のデプロイがないことを反する事実として挙げた
- 仮説 3：SMTP の一時的な停止（すでに戻っているかもしれない）
- 影響：4 通が自動では再送されない（`jobs.ts` の該当の行）。再設定のリンクは 60 分で切れる
- 復旧の選択肢：原因を直してから `jobs:retry`。**DLQ を戻すだけでは効かない**ことを、コードから指摘した。DLQ は証拠なので再実行の後に消す

### 評価

- 原因を 1 番目の仮説で当てた。根拠の行（ログ・トレース・コード）が正しく、確かめる方法も読み取りだけだった
- 資料の事実と推測を分けていた。`scripts/drill/` を「答えが書いてあるかもしれない」として自分から読まなかった
- 手順に足したこと（3・6 に反映）：資料に集めた時刻を書く、DLQ は数えるだけにする、パスワード再設定のリンクの期限と再実行の順番
- **指摘されて分かった問題（残す）**：失敗したメールのジョブの payload（宛先・本文・再設定のリンク）は、成功したときだけ消える作りで、失敗したものは DB に残る（第11章の作り）。DB を読める人には見える。失敗のまま一定の期間が過ぎたら payload を消す処理を足すか、リンクを payload に入れない作りにするかを決める
- 手元の障害は原因がはっきりしていて（1 種類のエラー）、本番の障害（複数の原因が重なる・ログが多い）より易しい。次は DB を止める・遅くする（web の 5xx と Worker の失敗が同時に出る）で試す
